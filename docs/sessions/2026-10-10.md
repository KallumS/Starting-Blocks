# Session log - 2026-10-10

## What changed

**A chord offers the inversions it has.** A triad two, a seventh three, a
ninth four, up to six for a thirteenth; the inversion puts the next note up
the stack in the bass and lifts the ones under it above it. Decision:
[0007](../decisions/0007-a-chord-has-as-many-inversions-as-notes.md). The same
engine went into Starting Blocks Notation, byte for byte, and from there into
Noterator and Miderator's Blocks toolbox.

## How it went

It started in Noterator: checking every Blocks chord against its Chords lane
(Noterator's 0046), and ScaleView Pro taking Blocks as its dictionary
(ScaleView's 0011). The user explained inversions along the way - the 2nd
puts the 5th in the bass, the 3rd the 7th and only for four-note chords, a
ninth has a 4th - and Blocks offered Root to 3rd on everything. Asked whether
to change it, the user set out the rule above.

**Two faults turned up writing the test, not before.** The sweep over every
chord, family, degree and inversion in four scales found the lifted notes
appended rather than in order (an Up arpeggio of an inverted ninth fell back
down at the top); a hand check of Cmaj9's 4th inversion found the root lifted
once still under the 9th, which was already true of the Elektra, Farben and
Mystic chords' 3rd inversion. Both fixed in `chordTones`.

**A hint naming the bass note was written and taken out.** "The 9th in the
bass" reads well on stacked thirds; on the rest an interval names two
members (six semitones a b5 or a #11, nine a 6th or a diminished 7th). A
wrong label is worse than an ordinal.

**The tests bite.** Against the old engine (with a stand-in count) seven of
the new checks fail; with the true count but the old lifting, the sweep
fails on the first inverted ninth; with the old fixed row in the window, the
panel test fails on a triad's "3rd" and a seventh's "4th".
